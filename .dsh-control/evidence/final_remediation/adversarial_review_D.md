### Q3. Does the canary verify `OLD_DB_ROWS_REQUIRED_AS_SEMANTIC_INPUT=0`?
**FINDING: The VALUE is correct at the code level, but the TEST's assertion is CIRCULAR — MEDIUM-severity defect.**

- `freertos_production_canary.json:39`: `"old_db_rows_required_as_semantic_input": "0"`.
- `test_freertos_production_canary.py:179`: `"old_db_rows_required_as_semantic_input": "0" if total_facts > 0 else ">0"`.
- **Defect (MEDIUM):** the field is *derived* from `total_facts > 0`, not independently measured. The test assumes that because M6 has facts, zero legacy-DB rows were required. It does **not** verify that the M6 facts actually *came from* direct materialization rather than legacy conversion.
- **Why the conclusion is still correct (mitigating):** the canary sets `FW_CONTEXT_M6_LEGACY_CONVERSION=0` (`test:66`), and `runner.py:1144-1146` only runs `index_legacy_db_into_m6` when `_m6_legacy_conversion` is True. In the canary config, that branch is skipped; the `elif _m6_store is not None` branch (`runner.py:1177`) runs `finalize_m6_world` instead, and the per-TU facts are produced by `materialize_unit_into_m6` (`_unit_processor.py:582`). So the *code path* genuinely does not require legacy-DB rows. The env config + code trace make the "0" claim TRUE, but the *test* does not prove it — a stronger test would (a) run with legacy DB present and absent and diff fact counts, or (b) assert that `materialize_unit_into_m6` was invoked and `index_legacy_db_into_m6` was not.

### Q7. What is the storage dedup ratio? (shared facts / total facts across builds)
**FINDING: Dedup MECHANICS verified; the >90%-at-scale RATIO is NOT measured — MEDIUM-severity gap.**

- `multi_build_world_test.json`: build_a=6 facts, build_b=6 facts, `shared_fact_dedup: true`.
- `test_multi_build_world.py:156-186` verifies dedup **mechanically**: `shared_func` (identical USR in both builds) resolves to **one** shared fact whose `m6_buildsets.build_names_json` contains *both* `buildA` and `buildB` (asserted at `:184-185`). This proves the BuildSet dedup design works — a shared fact is stored once and associated with multiple builds.
- **Defect (MEDIUM):** the test is a **2-file toy** (6 facts each, 1 shared function). The demonstrated dedup ratio is ~1/12 ≈ 8%, far below the stated ">90% at scale" success criterion. There is **no at-scale measurement** (e.g., mbed-os/Zephyr with hundreds of TUs and shared headers) anywhere in the evidence. The >90% claim is an *architectural argument* (shared headers/SDK code dedup naturally at scale), not a *measured* result.
- The economic viability of storage dedup is **plausible by design** (BuildSetStore stores each canonical fact once, keyed by canon hash, and BuildSets track ownership) but **unverified at production scale**.

### Q8. What is the frontend share? (facts materialized directly from libclang vs from legacy DB)
**FINDING: Implicitly 100% in the canary (verifiable from code path); NOT explicitly reported as a ratio — LOW-severity gap.**

- In the canary: `FW_CONTEXT_M6_LEGACY_CONVERSION=0` (`test:66`) ⇒ the legacy-conversion branch (`runner.py:1155`) is skipped ⇒ **all** 1756 facts come from `materialize_unit_into_m6` (`_unit_processor.py:582`), which reads `parsed.symbols`/`call_sites`/`references` directly from the libclang `ExtractionResult` (`m6_direct_materialization.py:90,179,208`). Every fact payload carries `"source": "direct_frontend"` (`m6_direct_materialization.py:131,141,151,167,197,223,246`).
- Therefore `frontend_share = 1756/1756 = 100%`. This **satisfies** the >70% (ideally 100%) criterion.
- **Defect (LOW):** the canary reports `direct_materialization_used: true` (boolean) and `m6_is_materialization_authority: true`, but does **not** report a numeric `frontend_share` ratio. A rigorous canary would emit `frontend_share: 1.0` (or `1756/1756`). The 100% figure is *inferrable* from the code path + env config, not *printed* by the canary.
- `direct_materialization_green_test.json` corroborates at toy scale: `facts_indexed_directly: 14, facts_reused: 0, legacy_db_created: false` ⇒ 14/14 = 100% frontend share.

### Q9. Are there any performance concerns with the per-TU direct materialization hook?
**FINDING: No blocking concern; minor inefficiency noted.**

- The per-TU hook (`_unit_processor.py:548-593`) runs **before** the legacy-DB lock section (`_unit_processor.py:595+`); it does **not** hold the legacy `write_lock`. Good — it does not serialize with concurrent indexers.
- `materialize_unit_into_m6` (`m6_direct_materialization.py:48-256`) is O(n) per TU (n = facts in that TU). Dedup is a dict lookup (`store._fact_cache.get(canon)`, `:170,199,225,247`) — O(1) per fact.
- **Minor inefficiency (INFO):** the hook calls `store.add_fact(...)` once per fact (`:171,200,226,248`) rather than `store.add_facts_batch(...)` (`m6_store.py:180`). For 1756 facts that is 1756 individual inserts vs 1 batched insert. Not a blocker at this scale; could matter for very large codebases (mbed-os ~60k symbols). The batch API exists and could be adopted.
- The store is opened once (Q5), so no per-TU open/close overhead.
- No N+1 query pattern observed — each fact is a single `add_fact` + cache check.

### Q10. Is there a benchmark comparing old (legacy DB conversion) vs new (direct materialization) approach?
**FINDING: NO benchmark evidence exists — MEDIUM-severity gap.**

- `runner.py:1156-1158` comments that the legacy-conversion path "exists for benchmarking against the old approach (§41)" — i.e., the *machinery* for a benchmark exists (set `FW_CONTEXT_M6_LEGACY_CONVERSION=1` to run the old path).
- A glob for `*benchmark*` under `.dsh-control/evidence/final_remediation/` returned **no files**. No timing, throughput, or memory comparison was produced.
- The "economic viability" claim in the task header implies a quantitative comparison; **none is on disk**. The direct path is *argued* to be viable (frontend share 100%, no legacy DB write), but no head-to-head timing (legacy conversion vs direct materialization on the same corpus) was recorded.
- This is the weakest part of the economic case. The architecture is sound, but "economically viable" is asserted, not measured.

## Does the Canary Prove Production Correctness?

**PARTIALLY — the end-to-end *pipeline correctness* is proven; the *economic-scale* claims are not.**

**Proven by the canary:**
- ✅ The real `runner.run()` executes on real FreeRTOS code (Q1).
- ✅ M6 facts are produced via **direct** materialization from libclang, not legacy-DB conversion (Q4, Q8 — `source: direct_frontend` on every fact; legacy-conversion branch skipped by env config).
- ✅ The legacy DB is **not created** in the v2-only default production mode (Q2 — `_legacy_compat_on()` defaults False; `open_db` never called).
- ✅ The M6 store is queryable with 1756 real facts, including genuine FreeRTOS API functions (Q4).
- ✅ The M6 store is opened once per run (Q5) and the World is correctly finalized after all TUs (Q6).

**NOT proven by the canary / evidence:**
- ❌ The 90%-at-scale storage dedup ratio (Q7) — only toy-scale dedup demonstrated.
- ❌ A head-to-head benchmark vs the legacy-conversion approach (Q10) — none exists.
- ⚠️ Rigorous independence from the legacy DB (Q3) — the *value* is correct but the *assertion* is circular.

## Recommendation

The core Issue-D claim — *the direct M6 materialization path works end-to-end and does not require the legacy DB* — is **VERIFIED**. I approve on that basis.

3. **(D-3)** Run the legacy-conversion vs direct-materialization benchmark on the same corpus and record timing.
4. **(D-4)** Have the canary emit `frontend_share` as a numeric ratio.
