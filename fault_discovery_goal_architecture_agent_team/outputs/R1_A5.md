- FACT F2: Goal contract requires source facts → fault hypotheses → rule candidates → verified rules with evidence + confidence + limitations; "from source code" is central; non-goals include perfect static analysis, solving compiler/linker semantics, perfecting fw-context, exhaustive RTOS modeling, eliminating human review [inputs/GOAL_CONTRACT.md; F-R0-20].
- FACT F3: Substrate query surface (allifdef-filtered, per-build): search_code/search_bodies/search_content (FTS5, match_lines), lookup_symbol, smart_search, semantic_search, find_variables; get_file_map/get_source/get_symbol_context/read_file/explain_symbol; call graph: find_callers/find_references/find_call_path/find_all_callers_recursive/find_callees_recursive/find_dead_code/find_hotspots/find_wrapper_callers/find_indirect_call_sites/find_indirect_targets/trace_data_flow (experimental); conditions: explain_condition (branch chain + macro_inputs with def_source) + list_conditional_regions; variants: compare_variants (5 dims, method:"text") + group_equivalent_variants (fingerprint = equality key only); get_vector_table; health: get_active_build/get_environment_status/list_variants/reindex_file/reset_index [docs/tools.md 532–2037].

- FACT F5: Passing surfaces per campaign: large public-project indexing, real stdio (cold 453–781 ms), call graph, hotspots, dead-code L1/L2 (with F-V1-005 caveat), semantic search, mutation integrity, honest empty results on unsupported archs, fanout 1→250 linear [F-R0-13].

- FACT F8: No Fault Discovery Agent code exists yet; only substrate + validation harnesses + this pack [F-R0-18].
- FACT F9: Standing anti-anchor rule: every proposed fw-context fix must state its impact on fault/rule discovery or it is not roadmap-critical [CONTRADICTIONS.json C-04 reconciliation].

## INFERENCES

- INF I1 (from F6): The seven substrate defects are not MVP blockers; each maps to a bounded Agent-side guard. The architecture can start now ("do not perfect the substrate first" is directly supported). Guard map: G1 provenance gate ↔ F-V1-003; G2 callback-chain uncertainty ↔ F-V1-004; G3 root-evidence gate ↔ F-V1-005; G4 single-line body fallback ↔ F-V1-007; G5 vector-table cross-check ↔ F-V2-001 + C-03; G6 existence re-verification ↔ F-V2-002; G7 chunked enumeration ↔ F-V1-008.
- INF I2 (from F3/F4): The substrate already covers the *evidence-extraction* layer of the goal pipeline (build understanding, acquisition, partial normalization); what is missing is everything above it: hypothesis, causality, rules, refutation, review. The Agent is an orchestration + reasoning layer, not a re-implementation of parsing.

C7 feedback: failed guards downgrade confidence or kill the hypothesis; never silently pass.

### PROPOSAL P2 — Substrate capability map for MVP

- NECESSARY: get_active_build/get_environment_status (gate); search_bodies/search_content (pattern layer, G4-aware); get_source/read_file (anchors, source_origin checked); get_symbol_context; find_callers/find_references/find_call_path/find_all_callers_recursive/find_callees_recursive; find_indirect_call_sites/find_indirect_targets (used with explicit uncertainty, G2); list_conditional_regions/explain_condition (config-condition evidence, F11); get_file_map; reindex_file (freshness); find_dead_code — NECESSARY only for the dead-logic family and only behind G3 (require root_evidence/linker-attested binary_status; else emit "unattested reachability", never a dead-code claim).
- OPTIONAL (MVP runs without): semantic_search/smart_search (recall aid; needs Ollama); compare_variants/group_equivalent_variants (divergence mining; single-variant MVP defers; multi-variant MVP requires them behind G1); explain_symbol llm_analysis (find-aid only, F10); get_vector_table (interrupt family; behind G5 until C-03 resolved); trace_data_flow (experimental); inheritance/template tools (C++-heavy projects); finetune/cache server/reranker (mature).
- REPLACEABLE / delegated (see P3): raw text sweep → grep; macro value access → controlled export/DB read (schema-version guarded) until F-V1-001 surface exists; build orchestration → build tools; LLM reasoning → Agent's own model.

### PROPOSAL P3 — Delegation map: what NOT to build in fw-context (answers OQ8)

| Concern | Delegate to | Rationale / boundary |
|---|---|---|
| Parsing, AST, per-TU flags, macro dump | libclang inside fw-context (already done) | No second parser in the Agent; substrate is the only C/C++ front end |
| compile_commands.json generation | Build tools (west/cmake/pio/make+bear) via `fw-context index --build` | Agent orchestrates subprocess; does not reimplement build logic |
| Raw-disk text sweeps: inactive-branch visibility, single-line definitions (G4), C-form vector presence (G5) | grep/rg in the Agent | fw-context ifdef-filtering is a feature, but fault discovery sometimes needs the text that does NOT compile or that the index dropped; grep is the complement, not a competitor |
| Cross-referencing alternative | clangd | NOT for MVP: duplicates the libclang surface, adds LSP complexity; revisit only if post-guard ref-defect rate is unacceptable |
| Pre-index triage of non-C artifacts (linker maps, Kconfig, .map) | tree-sitter or ad-hoc parsers in Agent | OPTIONAL later; MVP target is compiled C/C++ with build context, so priority is low |
| Linker semantics | Nobody (non-goal) | Do not solve; use build-attested linker evidence as a gate (G3) and emit uncertainty otherwise |
| LLM reasoning about mechanisms/rules | The Agent's own model | fw-context Ollama is convenience (llm_analysis, smart_search); per F10 it is never evidence |
| RTOS semantics (dispatch bridges, scheduler models) | Agent-side knowledge packs per RTOS | Non-goal forbids modeling RTOS inside fw-context; packs are data, not product code |

### PROPOSAL P4 — MVP vs mature

- MVP: single-variant or G1-provenance-gated multi-variant projects; fault families H1–H3; rule types R1+R2; refutation = G1–G7 checklist + small seeded-fault fixture set; output = markdown/JSON RuleCards with human gate. No embeddings dependency required (FTS5 surfaces suffice; semantic search is recall-only).
- Mature: multi-variant divergence mining (compare_variants at scale); R3/R4 rules validated against runtime traces; embedding finetune per project; FP-rate dashboards per rule family; per-RTOS knowledge packs; cache server for team-scale llm_analysis.

## ASSUMPTIONS
