## INFERENCES

- INFERENCE A4-I1 (C-01 ADJUDICATION — both verdicts TRUE under their own scopes, same code): READY_FOR_REAL_PROJECT_TRIAL means "no blocking product defects in the unit/integration/runtime-gate surfaces this wave tested; deferred items enumerated and excluded from the claim". NOT_READY means "the full semantic surface contains 7 product defects under a strict no-silent-error rule". The collision is rhetorical, not factual. The readiness statement that is TRUE for the substrate as an Agent evidence base: **fw-context @ d8f08a4 is fit for a BOUNDED, SCOPED real-project Agent trial — build-system-backed C/C++ projects, the FACT A4-F6 surfaces, under an evidence-discipline contract (INFERENCE A4-I5) — and is NOT fit for unconditional full-surface trust; bare-generator variant flows and uncorroborated empty/absence claims are excluded until F-V1-003 / F-V2-001 are fixed.** "Ready" without the scope qualifier, or "not ready" as a blanket bar on the Agent starting, are both wrong readings (C-04 anti-anchor).
- INFERENCE A4-I2 (C-03 RESOLVED — genuinely separate surfaces): FR-NEW-4 is a test-infrastructure/capability story about assembly-form tables on clang-less hosts; F-V2-001 is a product recognition gap for the C-form with capability present. No logical contradiction. The real shared residue is a CONSUMER-SIDE hazard, promoted to an Agent evidence rule: **an empty `get_vector_table` is ambiguous (honest skip | true absence | false absence) and must never be consumed as "this firmware has no interrupt surface" without corroboration** (lookup_symbol on `__VECTOR_TABLE`/`vectors`-style names, search_content for the array). Roadmap items touching vector tables must treat FR-NEW-4 (closed) and F-V2-001 (open) as separate work items.
- INFERENCE A4-I3 (blocking criterion used in the table): a finding is BLOCKING_FOR_AGENT_MVP only if all three hold: (a) it corrupts or fabricates evidence (not merely omits), (b) it sits on a surface the Agent MUST use for goal items 3–4 (configuration-condition reconstruction, rule derivation), and (c) no cheap in-harness cross-check can catch it. Only F-V1-003 meets all three. F-V2-001 and F-V1-005 fabricate/affirm falsely but have cheap cross-checks; F-V1-001/002/007/004 omit rather than fabricate; F-V1-006/008/V2-002/V4-001 are disclosed, bounded, or off the critical path.
- INFERENCE A4-I4 (root-class structure): the open findings collapse into three engineering clusters: (i) per-context data exists in the DB but is not exposed or is dropped at write time (F-V1-001, F-V1-002/007, F-V1-008) — one storage/exposure fix stream; (ii) variant isolation (F-V1-003) — generator-level fix plus self-check repair; (iii) claim-honesty of presence/absence (F-V2-001, F-V2-002, F-V1-005) plus surface completeness (F-V1-004, F-V1-006, F-V4-001). Cluster (i) is the largest quality lever; cluster (ii) is the only blocking one.
- INFERENCE A4-I5 (Agent harness can downgrade several findings without product changes): a thin evidence-discipline wrapper in the Agent (not in fw-context) can: treat `_fallback: true` rows as absent (F-V2-002→mitigated); treat count==cap as "truncated, rescope per-file" (F-V1-008→mitigated); cross-check empty vector-table/dead-code results before consuming (F-V2-001, F-V1-005→mitigated); supply entry roots itself for compile_commands-only projects (F-V1-005→mitigated). What the wrapper CANNOT fix is F-V1-003: the substrate certifies the wrong data, so no downstream check fires.
- INFERENCE A4-I6 (per EVIDENCE_RULES): none of the open findings justifies "perfect fw-context first" (C-04). Five findings are degrading-but-workable; exactly one blocks a specific flow; the correct posture is scope-then-trial, with the blocking flow fenced off, not a repair-first program.
